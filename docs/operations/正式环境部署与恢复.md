# 正式环境部署与恢复

正式环境与测试环境使用不同数据库、存储卷、Cookie 名称和访问端口。正式环境不导入演示工具，也禁止连接个人外部模型。

## 首次部署

1. 将 `.env.production.example` 复制为 `.env.production.local`，替换数据库密码、组织名称和管理员信息。`PLATFORM_STORAGE_HOST_ROOT` 必须是宿主机绝对路径，`BACKUP_ROOT` 必须位于另一块内部存储。
2. 运行 `pnpm deploy:production:config`。命令会先拒绝缺失值、示例密码、非安全 Cookie、个人 API Key 和非绝对存储路径，然后才解析 Compose。
3. 运行 `pnpm deploy:production:up`。网关默认只监听主机的 `8080`，应由公司内网入口或 VPN 再限制访问范围。
4. 执行 `pnpm bootstrap:admin:production` 创建首位维护人员。
5. 检查 `/health`、`/ready`、登录、上传分片、下载和回传预检。

## 上线门禁

代码和配置齐全后统一运行 `pnpm release:check`。它依次检查类型、Lint、自动化测试、生产构建和正式 Compose 配置；任何一项失败都不应上线。

这个命令不能代替外部依赖验收。正式开放 AI 组包前仍必须完成公司内部模型联调；正式接收员工工具包前仍必须接入企业病毒扫描；对公司开放前还必须验证内网入口、备份恢复和多 GB 压力测试。

## 备份

每天至少备份 PostgreSQL 和宿主机上的 `PLATFORM_STORAGE_HOST_ROOT`，两者必须来自同一时间窗口：

```bash
set -a
source .env.production.local
set +a
./scripts/backup-production.sh
```

正式 Compose 将该主机目录挂载到 API 容器的 `/data/platform`，因此备份脚本和 API 读写的是同一份文件，不再备份一个空的宿主机目录。备份目录包含数据库、自有文件和校验和，应按公司要求加密和限制访问。

## 恢复演练

恢复前停止 API，使用独立演练环境验证：

```bash
./scripts/restore-production.sh /path/to/backup/20260728-120000 --confirm
pnpm db:migrate
```

恢复后检查 `/ready`，抽查历史下载文件、已发布工具版本和回传附件。至少每季度做一次实际恢复演练；只有备份成功日志、不做恢复演练，不算可用备份。

## 大文件边界

客户端通过 `/v1/uploads` 创建会话，按服务返回的 `chunkSizeBytes` 上传分片，断线后查询会话并只补传缺少的分片，最后调用 `complete`。反向代理单请求限制为 9MB，是因为每个分片为 8MB；不需要把代理上限放到几十 GB。

当前压缩包文件和 ZIP 解压后总体积均限制为 20GB，这个契约同时用于前端说明、上传会话和预检。如果后续必须支持更大工具，应在对象存储、病毒扫描、容量配额和压力测试同时就绪后整体提升，不只修改页面文字。

上传完成后，工具上传和用户回传都通过持久化 `precheck_jobs` 进入后台预检。页面只轮询任务状态，不保持长请求。API 重启时会把处于 `running` 的中断任务恢复为 `queued` 再执行；任务结果和失败原因保留在数据库。

工具包生成会等待已经开始的本地构建后再优雅停机。如果进程被强制终止，下次启动会把遗留的 `generating` 记录改为可见的失败状态并提示重新生成，不会无限停留在“生成中”。

当前存储适配器使用平台持久卷。规模扩大或需要多 API 实例时，应把完成文件迁移到公司 S3 兼容对象存储，并保留同一上传会话协议。
