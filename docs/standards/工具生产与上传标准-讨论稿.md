# 工具生产与上传标准（讨论稿）

- 文档状态：持续讨论中，尚未定案
- 当前版本：v0.28
- 初始日期：2026-07-20
- 适用范围：平台维护人员上传、官方工具更新、用户净化回传、本地 Agent 调整或新生产工具
- 关联方案：[AI工具工作台产品方案-讨论稿](../product/AI工具工作台产品方案-讨论稿.md)

## 一、标准目的

平台中的工具可以是代码、Skill、Prompt、规则、模板、应用或组合工具，内部结构不必完全一致，但必须达到统一的可理解、可使用、可调整、可验证和可回传标准。

本标准用于保证：

- 普通用户能够理解工具能解决什么问题；
- 不同本地 Agent 能够找到统一入口并使用工具；
- 工具调整不会覆盖原始来源；
- 回传时能够识别组合工具和内部衍生组件；
- 平台 AI 能够准确建档、推荐和拆解；
- 平台维护人员能够低成本审核；
- 工具包不携带密钥、真实业务数据和无关运行文件。

## 二、适用资产

以下资产准备进入平台时均适用：

1. 平台维护人员上传的基础工具；
2. 官方工具的新版本；
3. 用户与本地 Agent 调整后的组合工具；
4. 从组合工具中拆出的衍生组件；
5. 本地 Agent 根据能力缺口新生产的工具；
6. 规则型、知识型、模板型和应用型工具。

## 三、核心原则

1. 原始来源可追踪，不直接覆盖来源工具；
2. 工具必须有通用 Agent 使用入口；
3. 必须说明能做什么和不能做什么；
4. 必须说明输入、输出和成功标准；
5. 必须说明依赖、联网、账号、费用和数据访问；
6. 必须有调整规则和版本变化记录；
7. 实际运行验证可以暂缺，但验证方法和真实验证状态不能缺失；
8. 不得包含密钥、真实业务数据和无关运行文件；
9. 新生产和调整完成后必须生成完成报告；
10. 缺少核心必填项或存在未处理敏感信息时不能发布。

## 四、标准随包分发

本标准必须完整放入平台生成的每一个包：

- 单个工具直接下载包；
- AI 组合工具包；
- 手动组合工具包；
- 缺失能力生产任务包；
- 用户净化回传包。

每个包在 `standards/TOOL_PRODUCTION_STANDARD.md` 保存适用标准全文，并在结构化清单中记录标准版本。本地 Agent 开始工作前必须先阅读该标准；新增、调整、拆分和回传工具均按同一标准执行。

标准文件不得被本地 Agent 删除、改写或替换。Agent 可以在完成报告中指出标准与实际任务的冲突，但不能自行降低准入要求。

### 4.1 标准版本兼容

- 已发布旧工具不因平台标准升级而被强制重新整理；
- 旧工具保留发布时适用的标准全文和标准版本；
- 旧工具可以继续展示和下载；
- 新上传工具必须符合提交时的最新标准；
- 官方工具新版本必须符合提交时的最新标准；
- 用户回传形成的组合工具、衍生工具和新组件必须符合提交时的最新标准；
- 平台新生成的组合包顶层携带最新标准，同时记录各组件原先符合的标准版本；
- 本地 Agent 如果修改旧组件，新产生的版本按最新标准整理，不能继续沿用旧标准豁免。

### 4.2 配套空白模板与合格示例

平台必须提供与本标准配套、可直接下载的标准空白工具模板。模板预先包含统一外层目录、核心文件、必填字段占位、填写提示和报告空表，可由维护人员手工整理，也可直接交给本地 Agent 按要求补齐。

空白模板采用“一套通用主模板＋按工具类型补充字段”的方式，不为每种工具形态建立彼此独立的基础模板：

- 所有工具共用相同的外层目录、身份、来源、能力边界、输入输出、调整、验证和回传字段；
- 确定工具类型后，再启用执行型、Prompt/规则型、模板型、应用型或组合型的补充说明和自动检查项；
- 同一个模板既可由维护人员手工填写，也可交给本地 Agent 根据工具文件整理；
- 工具类型发生变化时，不需要迁移到另一套目录，只需更新类型和对应补充字段。

每个工具只设置一个主类型，主类型决定必须补充的专用字段和自动检查规则。工具同时包含的其他形态通过多个能力标签表达，不重复套用多套完整模板。平台 AI 可以根据工具文件、入口和主要交付方式提出主类型及标签建议，但平台维护人员必须在正式发布前确认或修改。

主类型以用户的主要使用方式和主要交付形态为判断依据，不以工具包内部某类文件的数量为判断依据。判断时依次关注：用户从什么入口开始、主要通过什么方式完成任务、该工具对用户暴露的核心能力是什么。包内同时存在的代码、Prompt、规则和模板通过能力标签及对应补充字段记录。

平台还应提供合格示例工具包，用完整实例说明各文件应该写什么、写到什么程度，以及自动检查通过后的结构。示例用于帮助理解标准，不代表任何工具可以复制示例中的名称、能力、来源、验证结果或适用范围。

首批提供两个合格示例：

1. 单一执行工具示例：重点展示通用入口、运行依赖、输入输出、能力边界、验证方法、验证状态和修改规则；
2. 多组件组合工具示例：重点展示整体目标、组件清单及锁定版本、每个组件需要解决的问题、组成关系、来源关系、完成报告和净化回传结构。组合示例不预设固定执行顺序，具体规划仍由本地 Agent 完成。

- 模板和示例必须标明对应的标准版本；
- 标准升级时，应同步发布对应版本的模板和示例；
- 历史版本可以保留下载，用于维护符合旧标准的已有工具；
- 新工具、新版本和衍生工具默认使用提交时的最新模板；
- 使用模板或参考示例不能替代平台自动检查。

## 五、统一外层结构

所有工具使用以下统一外层结构：

```text
tool-name/
├── START_HERE.md
├── AGENT_INSTRUCTIONS.md
├── README.md
├── tool.yaml
├── CHANGELOG.md
├── lineage.yaml
├── return-manifest.yaml
├── standards/
│   └── TOOL_PRODUCTION_STANDARD.md
├── tool-files/
│   └── 工具实际业务文件...
├── policies/
│   └── modification-policy.yaml
├── validation/
│   └── validation.md
├── examples/
│   ├── input/
│   └── expected-output/
├── reports/
│   ├── completion-report.md
│   └── modification-report.md
└── ...
```

不同工具的代码、Prompt、规则、模板、应用和组合文件可以不同，但统一外层目录、核心文件名和结构化字段不可缺失。实际业务文件统一放入 `tool-files/`，或在 `tool.yaml` 中明确登记的等价目录。

### 5.1 双层使用入口

`START_HERE.md` 面向普通用户，必须保持简短易懂，至少包括：

- 这个包能帮助用户完成什么；
- 如何把完整工具包交给本地 Agent；
- 一段可直接复制给 Agent 的开始用语；
- 提醒用户等待 Agent 给出计划并确认后再开始。

`AGENT_INSTRUCTIONS.md` 面向本地 Agent，至少包括：

- 必须阅读的文件及顺序；
- 环境、权限和依赖检查；
- 开始前先输出计划并等待用户确认；
- 允许自动处理和必须重新确认的调整边界；
- 目标、输出和验证要求；
- 修改、完成和来源记录要求；
- 净化回传目录及敏感信息排除规则。

`START_HERE.md` 必须指向 `AGENT_INSTRUCTIONS.md`。两个文件均为自动检查必填项，不能只保留其中一个。

其中“开始用语”由平台在每次生成下载包时动态生成，不使用一条固定文案：

- 单工具包包含工具名称、能力、锁定版本和先阅读规则再规划的要求；
- 有明确目标的组合包包含整体目标、组件清单、各组件要解决的问题、期望交付和能力缺口；
- 没有填写目标的手动组合包要求 Agent 先阅读工具说明，再向用户确认目标后给出计划；
- 动态开始用语不得覆盖或缩减 `AGENT_INSTRUCTIONS.md` 的强制规则。

平台生成下载包时，还必须把同一份开始用语和简要操作步骤提供给下载完成页。页面至少说明：保留完整工具包、把完整压缩包或解压后的完整文件夹交给本地 Agent、复制开始用语、等待 Agent 先给出计划。网页指引和包内入口内容应来自同一份生成结果，避免描述不一致。

AI 组合工具包不得默认包含平台完整对话记录。包内任务上下文只能使用最终确认后的结构化结果，包括最终目标、已确认要求、未确认假设、限制条件、期望交付、未解决事项和能力缺口。已经被用户修正或否定的内容不得继续保留在 Agent 使用文件中。完整对话只保存在平台任务历史，不随包分发。

结构化任务上下文进入下载包前必须进行敏感信息检查：

- 密钥、Token、密码、Cookie、私钥等凭证类信息必须删除或替换为占位符，不能由用户确认后强行保留；
- 个人信息、客户名称、内部业务信息等内容必须被标记并提示风险，可以由用户确认保留、修改或删除；
- 平台生成的样例使用虚构或脱敏数据；
- 下载时经用户确认保留的信息，在净化回传时仍需重新检查，不能自动继承保留许可。

以下信息不可缺失：

- 通用入口；
- 工具说明；
- 结构化身份信息；
- 来源关系；
- 修改规则；
- 验证方法和状态；
- 版本变化；
- 完成或修改报告；
- 回传清单。

## 六、必填内容

### 6.1 身份与来源

- 工具名称；
- 版本；
- 工具形态；
- 来源工具 ID 和版本；
- 无来源时标记为新工具；
- 维护者或回传者；
- 创建和更新时间；
- 组合工具与组件关系；
- 来源、授权或使用范围说明。

### 6.2 能力与边界

- 能解决的问题；
- 适用场景；
- 不适用场景；
- 不支持的能力；
- 典型用户；
- 已知限制和风险。

### 6.3 输入与输出

- 必须提供的输入；
- 支持的文件或数据格式；
- 输出内容；
- 输出格式和目录；
- 输入缺失时的处理；
- 最小输入输出示例，无法提供时说明原因。

### 6.4 使用入口

- Agent 首先需要阅读的文件；
- 安装、启动或调用方法；
- 关键参数和默认值；
- 判断成功的方法；
- 常见错误和处理建议。

### 6.5 环境与权限

- 操作系统和运行环境；
- 依赖和安装方式；
- 是否联网；
- 是否需要 API Key 或账号；
- 是否产生费用；
- 读取、写入或上传的数据；
- 必须人工参与的环节。

### 6.6 调整规则

- 允许修改的参数和配置；
- 必须在副本中修改的内容；
- 不允许直接覆盖的内容；
- 必须重新询问用户的变化；
- 修改后需要更新的文档和版本；
- 回传记录要求。

### 6.7 验收与验证

- 工具层成功标准；
- 业务结果验收方法；
- 最小测试建议；
- 当前验证状态；
- 验证结果或未验证说明；
- 已知未解决问题。

### 6.8 版本变化

- 相对上一版本的变化；
- 输入输出变化；
- 依赖变化；
- 核心能力变化；
- 兼容性说明；
- 废弃或替换内容。

## 七、不同工具形态的补充要求

### 7.1 执行型工具

补充可执行入口、命令、参数、依赖、结果状态、错误日志位置和最小测试方法。

### 7.2 规则或知识型工具

补充触发场景、规则优先级、必须遵守和禁止事项、输出格式、参考材料边界和使用示例。

### 7.3 模板型工具

补充模板用途、必填字段、不可破坏区域、数据填充规则、导出要求和正确结果样例。

### 7.4 应用型工具

补充安装、启动、访问地址、停止方法、端口、环境变量、账号、网络、数据保存位置和故障处理。

### 7.5 组合工具

补充整体目标、组件清单及版本、每个组件需要解决的问题、最终交付标准和本地 Agent 规划要求。不预设固定执行顺序或节点连线。

### 7.6 待生产组件

现有工具无法覆盖的能力必须在任务包中登记为独立待生产组件，不得只保留无身份的零散提示词。待生产组件至少记录临时组件 ID、名称、需要解决的问题、预期输入输出、交付形态、验收目标、不可改变约束、数据边界、可复用参考和生产提示词。

待生产组件不是已发布工具，不得标记为可直接使用或计入工具采用统计。本地 Agent 完成生产后，必须把临时组件 ID 写入新工具的身份、来源和完成报告，并按最新工具标准补齐全部结构。回传审核通过后，由平台为其分配正式工具 ID 和版本。

存在多个能力缺口时，按照可独立复用和验收的能力边界拆分：输入输出不同、可以单独使用或可以分别验收的能力建立不同待生产组件；同一能力内部的规则、参数和实现细节不得机械拆成多个组件。每个组件独立记录临时 ID、生产要求和验收目标。

待生产组件表达必须解决的能力目标，不强制从零开发。本地 Agent 可以提出复用现有工具、增加配置、建立适配器或与其他组件合并，但必须对照原验收目标说明覆盖情况，在执行前取得用户确认，并保持原数据和安全约束。完成报告必须记录该组件最终属于新建、复用、适配、合并或未完成，以及对应验证结果。

回传资产按以下方式归类：

- 一次性参数或任务配置只保留在组合工具内部；
- 能独立复用的新适配器登记为新工具；
- 修改已有工具通用能力的结果登记为其衍生工具；
- 从零实现的待生产组件登记为新工具；
- 未发生变化的已有组件继续引用原版本，不重复建档；
- 达到组合工具准入要求的完整任务包可以登记为组合工具。

本地 Agent 的分类属于事实记录和建议，不直接决定平台资产。平台 AI 结合清单和文件差异生成拆分建议，维护人员审核后最终确认。

组合工具允许服务具体、小众场景，但必须满足最低可复用性：能够说明适用输入和场景；更换同类输入仍可重复使用；不包含原任务真实数据和专属信息；具有明确入口、交付结果和验收方法。仅包含一次性结果、运行现场、日志或不可复用过程的包不能作为平台组合工具发布。

与已有工具相似的回传不得自动合并或覆盖：有明确来源的登记为衍生工具；只包含缺陷修复或兼容调整且目标、边界、输入输出未实质变化的，可以由维护人员认定为原工具新版本；目标或能力明显不同的保留为衍生或独立工具。没有来源但高度相似时，平台 AI 只提供相似工具和差异提示，由维护人员最终判断。原始回传与判断记录必须保留。

贡献者公开署名、荣誉展示和采用反馈归属暂不在首期标准中规定。平台只需保留上传者、原回传、最终工具或版本关系及审核记录，确保来源可追溯。

## 八、本地 Agent 生产过程

本地 Agent 新生产或调整工具时必须：

1. 读取用户确认的目标；
2. 检查是否可以复用现有工具；
3. 向用户展示生产或调整计划并等待确认；
4. 保留来源工具，在副本中调整；
5. 先定义能力边界、输入和输出；
6. 使用最小样本生产和验证；
7. 补齐通用入口、说明、验收、版本和调整规则；
8. 生成完成报告与修改记录；
9. 清除业务数据、密钥、日志、缓存和临时文件；
10. 输出符合标准的 `return-package/`。

## 九、完成报告

`completion-report.md` 必须包含：

- 用户确认的最终目标；
- 实际使用的工具及版本；
- Agent 实际执行计划摘要；
- 完成的目标；
- 最终交付物说明；
- 配置、适配和修改；
- 新生产、替换或移除的工具；
- 验证方法和结果；
- 未完成目标和已知问题；
- 复现方法；
- 净化回传包状态。

报告不得嵌入真实业务数据、密钥或敏感交付文件。

## 十、净化回传

默认保留：

- 调整后的工具；
- 新生产组件；
- 通用配置和适配器；
- 工具说明、规则和目标模板；
- 来源和回传清单；
- 完成报告、修改报告和验证结论；
- 脱敏或模拟样例。

默认排除：

- 用户真实输入；
- 最终业务交付物；
- API Key、账号、令牌、Cookie 和认证文件；
- 日志、缓存、临时文件和本地环境；
- 个人信息、客户信息和部门敏感数据；
- 无关历史实验和失败产物。

## 十一、平台准入检查

平台依次进行：

1. 结构完整性检查；
2. 敏感信息与安全检查；
3. 来源和组件关系检查；
4. 说明文件与实际内容一致性检查；
5. AI 缺失项和风险分析；
6. 维护人员确认或审核。

平台 AI 只输出缺失项、冲突、敏感信息风险和整理建议，不自动补齐必备文件，不重写工具说明，也不把原始目录自动改造成标准发布包。维护人员自行整理工具后重新提交检查。

检查结果统一分为：

1. **必须修复**：涉及敏感凭证、核心结构、身份来源、输入输出、通用入口或严重一致性冲突；存在时阻止提交和发布；
2. **风险提醒**：涉及未实际验证、不稳定依赖、边界不清和已知未解决问题；允许继续，但必须保留并如实展示状态；
3. **优化建议**：涉及文案、示例、目录可读性和非核心说明，不影响提交。

平台不得把优化建议作为检查失败原因，也不得由 AI 自行将必须修复项降级。修正提示词优先列出并处理必须修复项，可同时附带其他两类结果供参考。

工具发布后，风险结果按受众分层：

- 会影响安装、使用、费用、网络、数据安全、兼容性或结果可靠性的风险提醒必须向普通用户展示；
- 工具卡片展示简短风险标识，工具详情页展示完整原因、影响范围和处理建议；
- 组合包确认页再次汇总组件中的关键风险；
- 优化建议、内部检查过程和已修复历史问题仅在维护后台及审计记录中保留，不作为当前版本的对外风险展示。

以下高影响风险需要在下载前由用户汇总确认：

- 文件或数据会传输到外部服务；
- 会产生付费 API、订阅或其他费用；
- 需要账号、密钥、管理员权限或修改系统环境；
- 已知问题可能明显影响预期交付结果。

未实际验证、普通联网、一般依赖和兼容性限制仅醒目展示，不作为强制确认项。组合包对所有组件的高影响风险去重汇总后一次确认，不要求用户逐个工具重复勾选。

风险确认是否在同一用户重复下载、工具版本变化或风险内容变化时复用，暂不在首期标准中细化。第一版只要求下载前完成一次当前包的高影响风险汇总确认，后续再设计确认快照、失效和审计规则。

平台不提供在线工具文件编辑能力。维护人员在本地补齐、清理和重组后重新上传；平台重新执行全部准入检查，并保留历次上传与检查记录。平台在线界面只允许编辑工具展示资料、标签、模块归属和发布配置。

### 11.1 普通用户回传的预检查

普通用户的净化回传包必须先通过自动预检查，才能进入维护人员审核：

- 未通过时不创建正式审核中记录；
- 不进入维护人员待审核列表；
- 平台输出缺失项、风险和可交给本地 Agent 的修正清单；
- 用户在本地修正后重新上传；
- 通过后才进入 AI 拆解和人工审核；
- 发现密钥、认证信息或真实业务数据时立即阻止提交，不将风险文件作为长期平台资产保存。

回传包只有存在“必须修复”项时才视为预检查未通过。仅存在风险提醒或优化建议时可以进入审核，风险结果随回传记录一并交给维护人员判断。

预检查失败时，平台同时生成：

1. 面向用户的缺失项和风险说明；
2. 可一键复制或下载为 `FIX_PROMPT.md` 的本地 Agent 修正提示词。

修正提示词必须包含标准版本、失败项、相关文件位置、修正动作、禁止改变项、敏感数据限制、需要重新生成的清单和最终净化包要求。平台只生成提示词，不执行修正。

以下情况不能发布：

- 缺少通用入口；
- 缺少能力边界；
- 缺少输入输出；
- 缺少使用方式；
- 缺少验证方法或验证状态；
- 缺少版本和来源信息；
- 缺少完成或修改报告；
- 存在未处理的密钥、真实业务数据或敏感文件；
- 结构化清单与实际文件存在严重冲突。

没有实际运行验证本身不阻止发布，但必须标记为未验证。
